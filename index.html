What this is

The ESP32 Bit Pirate is a 25-mode hardware-hacking workbench — I2C, SPI, JTAG, Sub-GHz, LoRa, RFID, Wi-Fi and more — controlled through a single text console. This project wraps that console in a gateway daemon so the device can stay wired into one machine permanently while being driven from anywhere on the network: a browser, an MCP-speaking agent, or a terminal.

It authors no new device behavior. Every command the gateway can send is a command the firmware's own console already accepts — this is a transport layer, not a new capability.

Three primitives, every mode

The firmware's console turns out to only ever do one of three things after you send it a line. The whole system is built on recognizing which, and handling each correctly.

run()

Send a line, read until the mode prompt (I2C> ) settles. For single-shot commands — hex, discovery, status.

stream()

Send a line, then yield output continuously until stopped. For scan, sniff, monitor — anything that loops until Enter or Ctrl-C.

open_session()

Send input, read whatever's buffered, repeat. For choice menus, first-time pin config, and raw full-duplex bridges.

Why three, not one

A naive "send a line, wait for the prompt" model breaks the moment a command asks a question — switching into I2C mode for the first time doesn't reply Mode changed to I2C at all; it asks for SDA pin, SCL pin, and frequency first. open_session() exists because that distinction is load-bearing, not cosmetic.

System design

One owner of the wire.
Everyone else talks over the network.

The device plugs into one host via USB, permanently. A single daemon owns that serial connection exclusively. Every other client — webapp, agent, CLI — is a network client of the daemon, authenticated by bearer token, and never touches the device directly.

Why not just use the device's own Wi-Fi console?

The firmware already serves a web terminal over its own Wi-Fi (ws://<device-ip>/ws). It was the first design considered, and rejected for three concrete reasons found in the firmware's source, not assumptions:

  • No authentication. Anyone who can reach the device's IP controls it.
  • Single-client eviction. A second WebSocket connection silently disconnects the first — there is no real arbitration between simultaneous clients.
  • Self-disconnecting commands. Running deauth or flood in WIFI mode reconfigures the device's own radio — the same radio carrying the control session. The firmware's own source code warns about exactly this.

Routing control over USB instead sidesteps all three: USB is a dedicated wired link unaffected by what the device's radio is doing, and the gateway enforces real arbitration (one controller at a time, explicit rejection otherwise) in code instead of leaving it to the device's own WebSocket eviction behavior.

The one thing that still needs Wi-Fi

File storage (captured IR/Sub-GHz/LoRa profiles, scripts) lives on the device's LittleFS filesystem, exposed only through the device's own HTTP API — there's no serial command for it. The gateway proxies that one feature over the device's Wi-Fi, so network clients still never reach the device directly; they reach the gateway, which reaches the device.

Single-controller arbitration

Streaming and interactive sessions are exclusive: only one network client can hold the controller lock for /api/stream, /api/session, or /api/term at a time. A second request while one is active gets an explicit stream busy response naming the current controller — not a silent takeover, and not a queue.

Getting started

Running in under a minute

Plug the device in once. Start the gateway once. Everything after that is a network call.

  1. Install

    # from the project root
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

  2. Start the gateway

    Auto-detects the console port by USB vendor/product ID, and generates a bearer token into ~/.config/bitpirate/gateway.toml on first run.

    .venv/bin/python -m bitpirate.gatewayd
# INFO  Using serial port /dev/ttyACM0
# INFO  Gateway token: 122a1be3d376...
# INFO  Uvicorn running on http://0.0.0.0:8420

  3. Drive it from the CLI

    .venv/bin/bitpirate exec "hex 255"
.venv/bin/bitpirate mode i2c
.venv/bin/bitpirate exec "discovery"
.venv/bin/bitpirate stream "scan"        # Ctrl-C to stop
.venv/bin/bitpirate repl               # full interactive terminal

  4. Or open the webapp

    open http://<gateway-host>:8420/
# asks for the token on first load, then remembers it

  5. Or register the MCP server

    .mcp.json is already set up for this repo — Claude Code (or any MCP client) picks it up automatically.

    {
  "mcpServers": {
    "bitpirate": {
      "command": "/path/to/.venv/bin/python",
      "args": ["-m", "bitpirate.mcp_server"]
    }
  }
}

Run it as a service

So it survives reboots, with the USB cable permanently attached:

mkdir -p ~/.config/systemd/user
cp bitpirate-gatewayd.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now bitpirate-gatewayd
loginctl enable-linger "$USER"   # keeps running without an active login

HTTP & WebSocket API

Every route under /api/* requires a bearer token — either Authorization: Bearer <token> (HTTP) or ?token= (WebSocket, which can't set headers). The gateway binds 0.0.0.0 by default; the token is the actual security boundary, not the interface binding.

RouteDescription
/api/deviceGETConnection status, current mode, firmware ref, who (if anyone) holds the controller lock.
/api/modesGETThe full generated mode spec — every mode, command, kind, and tier.
/api/runPOSTTransactional command. Body: {cmd, confirm, timeout}. 409 if the command turns out to need multi-turn interaction; 403 if approval-required without confirm.
/api/mode/{name}POSTSwitch mode.
/api/interruptPOSTSend Ctrl-C.
/api/resetPOSTHardware reset (~8s). See Recovery & reset.
/api/streamWSStreaming command. Query: cmd, token, confirm. Send any text to stop. Single-controller: a second concurrent request gets a stream busy error.
/api/sessionWSInteractive session. Same query params. Send lines to answer prompts; __close__ to end.
/api/termWSRaw full-duplex terminal passthrough — every mode, every command, as if typing directly.
/api/fs/listGETList LittleFS files. Needs wifi_host configured — 503 otherwise.
/api/fs/uploadPOSTUpload a file (raw body, ?file=).
/api/fs/downloadGETDownload a file (?file=).
/api/fs/deleteDELETEDelete a file (?file=).

Example: run, then stream

# transactional
curl -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"cmd": "hex 255"}' http://127.0.0.1:8420/api/run
# {"output": "...Dec: 255\nHex: 0xFF\nBin: 11111111", "mode": "HIZ"}

# streaming, over websockets
wscat -c "ws://127.0.0.1:8420/api/stream?cmd=scan&token=$TOKEN"

A rejected approval-required call

curl ... -d '{"cmd": "erase"}' http://127.0.0.1:8420/api/run
# 403
# {"detail": "'erase' in mode RFID is tagged approval-required
#            (destructive or offensive). Resend with confirm=true."}

MCP tools

A thin network client of the gateway — it never touches the serial port, so it can run on a different machine than the one with the USB cable. 16 tools, exercised over real JSON-RPC/stdio protocol messages, not just imported and inspected.

Authorized use

Bit Pirate includes RF/wireless and offensive modes — WIFI deauth/flood, Sub-GHz bruteforce/jam, RFID clone. These tools are a faithful pass-through to the device's own existing CLI; they author no attack logic. Approval-required commands need confirm=True and are otherwise rejected. Use only on hardware, devices, and networks you own or are explicitly authorized to test.

Interface

Webapp

Served directly by the gateway at / — no separate build step, no separate host. Three tabs, all driven by the same API surface documented above.

Terminal
Full REPL over /api/term — every mode, every command, raw instruction syntax. Shared: only one client controls it at a time.
Modes
Every mode and command from /api/modes, with run/stream buttons and a confirmation dialog for approval-required commands.
Files
LittleFS browser over /api/fs/* — list, download, delete. Needs the device on Wi-Fi.

The token is requested once on first load and kept in the browser's local storage for that origin — it never leaves the device it was entered on.

Device model

Safety tiers

Every command in the generated spec carries a tier. Destructive target operations and offensive RF/network commands need an explicit confirm — rejected with the reason otherwise, not silently run.

65read-only
179allowed
19approval-required
TierMeaningExamples
read-onlyReads, scans, dumps. Never changes device or target state.scan, discovery, regs, pins
allowedWrites or configures, but isn't destructive or offensive by name.config, send, connect
approval-requiredDestructive target ops or offensive RF/network. Needs confirm=true.erase, deauth, flood, jam, clone, bruteforce

Double-gated, mode-scoped

The gate is scoped to the command's actual mode — erase is approval-required in RFID mode, but a bare erase sent while in I2C mode isn't a recognized I2C command at all, so it falls through to the default tier rather than matching by name alone. Where the device itself prints its own confirmation prompt, the gateway drives that too: confirm=true isn't treated as sufficient on its own.

Approval tier is adopted, not invented

The three-tier model mirrors Indigaz/bitpirate-mcp's approval-gating design — a proven pattern, not a novel one.

Device model

Hardware you'd add

HIZ, DIO, LED (as a mode), BLUETOOTH, WIFI, and GENERAL work with nothing extra — onboard radio and GPIO cover them. Everything below needs a module wired in. Chip choices are confirmed against the firmware's own wiki, not guessed — e.g. RFID is the PN532 over I2C, not the RC522/SPI reader most projects default to.

Pin conflicts are real

I2C (SDA 6) and 1-Wire (GPIO 6) collide on firmware defaults. CAN's CS pin is hardcoded, not reconfigurable. For a permanent multi-peripheral build: give every SPI device its own CS off the shared MOSI/MISO/SCLK bus, and reconfigure via each mode's config command rather than assuming defaults coexist.

Four of these transmit, not just listen

SUBGHZ, LORA, FM, and CELL all key up an actual radio. The firmware's own LoRa wiki page: "RF transmission may be regulated depending on frequency, power and local legislation." Same logic applies to the other three — check your region's rules, same spirit as this project's authorized-use note.

Board-specific gotchas (Lonely Binary Gold Edition + PinPulse Shield)

The tables below give GPIO numbers; these are specific to this exact board and where those numbers actually land on it — drawn from a companion project's hardware research on the same board (electronics_bench's docs/bitpirate-notes.md), cross-referenced against the vendor's own net-list pages, not just assumed.

Don't wire anything to these 12 pins

0, 3, 19, 20, 22–37, 43, 44, 45, 46, 48 — strapping pins sampled at boot (0, 3, 45, 46), native USB (19, 20), the octal PSRAM "trap" (35–37, pads are on the header), the serial bridge (43, 44), and the onboard RGB LED (48). A board that flashes fine but won't boot on its own power is almost always one of 0/3/45/46 held at the wrong level at power-up.

Where the defaults physically are
Left edge (display end)3V3, 3V3, RST, 4, 5, 6, 7, 15, 16, 17, 18, 8, 3, 46, 9, 10, 11, 12, 13, 14, 5V, GND
Right edgeGND, 43, 44, 1, 2, 42, 41, 40, 39, 38, 37, 36, 35, 0, 45, 48, 47, 21, 20, 19, GND, GND

Every default pin in the tables below (UART 17/18, I2C 6/7, SPI 10–13, IR 4/5) is on the left edge. The shield passes every pin through hole for hole — a male pin and a female socket on the outer edge carry the same net, so no soldering is needed to wire a module in.

The board's printed marks don't match the firmware's defaults

Silkscreen/Arduino convention: I2C SDA 8 / SCL 9, SPI MOSI 11 / MISO 13. Bit Pirate's actual defaults: I2C SDA 6 / SCL 7, SPI MOSI 13 / MISO 11 (swapped relative to the marks). Both work electrically — the firmware sets every pin explicitly via each mode's config — but wiring to the printed label instead of the firmware's actual default pin is the mistake to watch for.

Two diagnostics worth knowing before you assume something's broken

  • A floating pin flickers. The shield's LEDs have no pull-ups — each GPIO feeds a 74HC04 inverter input (~1µA), so a pin nothing is driving visibly flickers or glows when a hand comes near. That's the floating input, not a fault.
  • UART leaves an internal pull-up on RX that the DIO pin table doesn't show — a shield LED can stay lit after you leave UART mode. A hiz / explicit pin reset clears it.

Power budget: the 3V3 rail is an AMS1117 shared with the module, the USB bridge, and (on the shield) all 36 LEDs — roughly 500mA left for your own parts. Worth keeping in mind for the LED strip and cellular modem below, both of which can pull real current; a separate 3.3V/5V supply for those is the safer default.

Device model

Recovery & reset

UART/HDUART bridge mode has no typed exit on this board — it only responds to a physical button, and the board this was built against (a Lonely Binary PinPulse Shield) doesn't have one. reset_device() exists because of that.

What actually works, found by testing, not assumed

A plain DTR/RTS pulse — the textbook ESP32 auto-reset mechanism — was verified via continuous USB bus polling to have zero effect on this board's native USB-Serial-JTAG peripheral. What works instead: shelling out to esptool with retries, then waiting out the firmware's own boot-time "Press any key to start..." gate.

AttemptedResult
Raw DTR/RTS pulse (textbook timing)No effect — confirmed via continuous lsusb polling across the call.
esp_pylib's own USB-specific timingAlso no effect, called in isolation.
esptool's HardReset strategy class directlyStill no effect — the retry wrapper alone wasn't the missing piece.
Full esptool ... chip-id CLI invocationWorks — but not always on the first attempt; one in three hit a genuine mid-reset ENODEV.

The shipped implementation shells out to the full esptool flow with its own retry loop, then actively waits for the boot banner and a settled prompt before returning — about 8 seconds end to end, confirmed to leave the device in a genuinely clean state rather than just timed around.

When to use it

  • A wedged bridge session with no other way out.
  • A dangling interactive session left by an abruptly-closed client — closing a session releases the gateway's controller lock, but not the device's own pending state.
  • Any other unresponsive state.
.venv/bin/bitpirate reset
# resetting (this takes ~8s)...
# {"ok": true, "mode": "HIZ"}

Status

Verified vs. known gaps

Tested against a real ESP32-S3 Gold Edition + PinPulse Shield (Lonely Binary), firmware v1.8, native USB-CDC console — not just written and assumed to work. Read this before trusting anything here blind.

Verified against real hardware

  • Core protocol. Single-\r line termination (not \r\n — the trailing \n gets silently consumed as an extra Enter by whatever reads next), settled-prompt vs. sub-prompt detection, carriage-return redraw collapsing. Verified across transactional, streaming, and interactive command shapes.
  • set_mode(). Confirmed on a mode needing first-time pin config (I2C) and one that doesn't (direct reply). Handles both transparently.
  • reset_device(). See Recovery & reset for the full story — confirmed to leave a genuinely clean, immediately-usable connection, not just a timed delay.
  • Gateway. Bearer-token auth, mode-scoped approval gate, /api/run, /api/stream (including stop-on-disconnect even when the client is killed abruptly), /api/session, /api/reset — all driven over real HTTP/WebSocket calls, not mocks.
  • CLI and MCP server. Both tested as real clients; the MCP server via actual JSON-RPC/stdio protocol messages.
  • Mode spec. Generated at the v1.8 tag, cross-checked by hand against several controllers (RFID, WIFI, CAN, I2C).

Known gaps

LittleFS file transfer

Source-verified against the firmware's exact JSON response shape and all four HTTP handlers, but never exercised against a live device — it requires the device's own Wi-Fi SSID/password, which this build doesn't have on file.

Device-side session cleanup

Closing a session or stream releases the gateway's controller lock, but not the device's own pending state — confirmed live: closing mid-rfid write leaves the device sitting at that sub-prompt for whoever connects next. reset_device() is the reliable recovery.

Webapp

Every API call it makes is separately verified working, and the embedded JS is syntax-checked — but it has never been opened in an actual GUI browser in this build environment.

Out of scope by design

Firmware (re)flashing needs bootloader-mode access that conflicts with the gateway's exclusive hold on the serial port. Not wired up in this pass.
